# 本地分支合并编排与版本发布规划

以本地导入的提交、分支与标签数据为输入，计算：

- **多条发布线**各自的下一语义化版本号与变更日志，以及跨线统一执行顺序；
- 同一批分支的**合并式 / 变基式**两种集成顺序；
- 所有结论在不同操作顺序下保持一致，并输出可解释的判定依据（`rationale`）。

## 模块结构

| 模块 | 职责 |
| --- | --- |
| `release_planner/models.py` | 数据模型：`Commit` / `Tag` / `SemVer` / `MergePlan` / `LinePlan` / `MultiLinePlan` |
| `release_planner/graph.py` | 提交图导入、校验（缺失父提交、循环父边、重复提交）与拓扑查询 |
| `release_planner/planner.py` | 合并式顺序、下一版本号、变更日志与判定依据 |
| `release_planner/lines.py` | 多发布线编排：各线独立版本基线、无关标签忽略说明、跨线统一顺序 |
| `release_planner/integration.py` | 变基式集成：直线化顺序、合并提交丢弃说明、不可变基结构拒绝 |
| `release_planner/store.py` | 线程安全存储、原子批量导入、导入修订号、历史快照回溯、旧格式兼容 |
| `main.py` | FastAPI HTTP 接口 |

## 提交图导入与校验规则

- 提交按 `id` 唯一存储。导入内容完全相同的提交为**幂等操作**（返回 `added=0`）；
  `id` 相同但内容不同判定为冲突，拒绝并返回 `duplicate_commit`，不静默覆盖。
- 规划前执行校验，任一非法输入立即拒绝，不跳过、不截断：
  - `missing_parent`：某提交声明的父提交不在图中；
  - `cyclic_parent_edge`：父边构成环（错误信息给出环路径）。
- 合并提交（多个父提交）天然由拓扑排序支持。

## 多发布线的版本基线规则

`plan_lines(graph, tags, lines)` 接受 `{线名: {分支名: 头提交}}`：

1. **每条线的基线只看自己的历史标签**：标签指向的提交必须落在该线任一分支头的
   可达历史内，才参与该线的基线计算。别的线上的标签（如另一条线的 `v2.0.0`）
   不会抬高本线的版本号。
2. 被忽略的标签逐条列入该线结果的 `ignored_tags`，并说明原因
   （“指向提交 X，不在发布线 Y 任何分支的可达历史内”），整体 `rationale` 中
   也有汇总，忽略行为可审计、不是静默丢弃。
3. 各线的待发布集合、下一版本与变更日志由同一套 `ReleasePlanner` 规则在
   过滤后的标签集合上独立计算，线间互不影响。
4. **跨线统一执行顺序**：几条线共用已发布历史时，取所有线待发布提交的并集，
   在整体可达子图上做确定性拓扑排序（父先于子，同层按提交 id 字典序）。
   共享的已发布部分不出现，共享的待发布提交只出现一次；该顺序与传线、
   传分支、导提交的先后顺序无关。

## 两种集成方式的顺序判定与失败条件

同一批分支可以分别取两种可执行顺序：

**合并式**（`ReleasePlanner.plan`，`GET /plan`）：

1. 分支头可达提交减去所有标签提交的祖先集合，得到待发布集合；
2. 拓扑排序：**父提交必先于子提交，合并提交在两个父提交之后**，合并点保留；
3. 同层多个候选按提交 id 字典序出队，输出唯一确定。

**变基式**（`rebase_plan`，`GET /plan/rebase`）：

1. 待发布集合与合并式一致；
2. 待发布集合中的**普通合并提交（2 个父）被丢弃**——两侧历史都会被拉直保留，
   只有合并点本身消失，被丢弃的提交列入结果的 `skipped` 并在 `rationale`
   中逐条说明；
3. 保留提交按同一套确定性拓扑序拉成一条直线；版本与变更日志只统计实际
   会重放的保留提交（被丢弃合并提交上的变更级别不抬版本）；
4. **失败条件**：待发布集合中出现**八爪鱼合并（≥3 个父提交）**时，无法拉成
   语义明确的直线，以 `unrebaseable` 拒绝——该原因与普通输入错误
   （`unknown_branch`、`empty_plan` 等）是不同枚举值，调用方可明确区分；
   不会返回一个看似可执行、实际跑不了的顺序。同一输入走合并式不受影响。

## 批量导入与导入修订号语义

- **原子性**：`import_batch`（`POST /batches`）把一批提交 + 标签 + 分支当作整体，
  先在副本上应用并校验（提交冲突、父提交缺失/成环、标签或分支指向不存在的
  提交），任一失败则**整批不生效**，仓库状态与导入修订号都保持原值，
  不存在部分导入。
- **修订号单调递增**：仅在批次真正引入新内容（新提交/新标签/分支指针变化）
  时 +1；同一批数据重复导入、或只含已有内容的批次，修订号**不空涨**。
- **增量查询**：`commits_since(rev)`（`GET /commits/since/{rev}`）返回从修订号
  `rev` 到现在新增、且**尚未发布**（不属于任何标签祖先集合）的提交，
  按拓扑序输出。同一提交只在首次导入的修订号计入一次，重复导入不会让它
  再次出现在增量里；之后被打标签发布的提交会从增量结果中消失。
  修订号越界（负数或大于当前值）以 `invalid_revision` 拒绝。
- **并发语义**：所有读写在同一把互斥锁内完成，整批应用在锁内原子生效；
  并发导入不丢数据、不重复应用，每个生效批次拿到唯一的修订号，
  内容与修订号一一对应。
- **快照兼容**：修订号与每个提交的首导入修订号都纳入快照，`checkout` 回溯后
  修订号与增量查询结果与当时完全一致。

## 与旧数据的兼容范围

- `import_records()` 兼容旧格式字典记录，字段缺失时使用稳定缺省值：
  `parents=()`、`message=""`、`branch=""`、`change="patch"`。
- 旧有的逐条接口（`POST /commits` `/tags` `/branches`）保留，语义不变，
  同样会推进导入修订号；旧的快照回溯（`POST /snapshots` `/checkout/{ver}`）
  行为不变，且回溯后修订号一并恢复。
- 既有规划接口 `GET /plan` 输出结构新增 `skipped` 字段（合并式下恒为空列表），
  其余字段含义不变。

## 版本计算规则

版本遵循 SemVer 2.0.0：`MAJOR.MINOR.PATCH[-prerelease][+build]`。

1. **基线版本**：将（本线）标签按 semver 规则排序后取最高者；无标签时为 `0.0.0`。
   - 比较顺序：核心号 → 预发布段；有预发布段者**低于**同核心号正式版；
     预发布段逐段比较，纯数字段按数值、字母段按字典序，数字段低于字母段，
     公共前缀相同时段数多者更高（`rc` 系列标准顺序）。
   - **构建元数据（`+build`）不参与排序**，仅保留在输出中。
2. **待发布变更级别**：取待发布提交 `change` 字段的最高级别
   （`major > minor > patch > none`）。
3. **下一版本**：
   - 无待发布提交：保持基线不变；
   - 基线是**预发布版本**（如 `1.0.0-rc.1`）：待发布变更并入这一未完成的发布，
     下一版本**毕业为正式版**（`1.0.0`），并丢弃构建元数据；
   - 基线是正式版本：按最高级别提升一次，并清除预发布/构建元数据。
4. **幂等**：重复导入同一提交不会在图中产生第二条记录，因此既不会重复计入
   变更日志，也不会重复提升版本号。

## 失败原因一览

| reason | 触发条件 |
| --- | --- |
| `duplicate_commit` | 同一 id 以不同内容重复定义 |
| `missing_parent` | 父提交缺失 |
| `cyclic_parent_edge` | 父边成环 |
| `unknown_branch` | 分支头提交不存在 |
| `unknown_tag` | 标签指向的提交不存在 |
| `invalid_version` | 版本号无法解析 / 历史版本号越界 |
| `empty_plan` | 未提供任何分支 / 发布线 |
| `unrebaseable` | 待发布历史含八爪鱼合并等不可拉直结构（仅变基式） |
| `invalid_revision` | 增量查询的修订号越界 |

## HTTP 接口

```text
POST /commits              批量导入提交（原子，幂等，返回 added 与 revision）
POST /batches              原子批量导入提交+标签+分支（整批生效或整批拒绝）
GET  /revision             当前导入修订号
GET  /commits/since/{rev}  从 rev 到现在新增且未发布的提交（拓扑序）
POST /tags                 添加版本标签
POST /branches             设置分支头
GET  /plan                 合并式顺序、下一版本、变更日志与判定依据
GET  /plan/rebase          变基式直线顺序（skipped 列出被丢弃的合并提交）
POST /plan/lines           多发布线规划（body: {"lines": {线名: [分支名]}}）
POST /snapshots            显式生成快照，返回版本号
POST /checkout/{ver}       回溯到历史版本（修订号一并恢复）
```

错误响应形如：`409/404/422 {"detail": {"reason": "unrebaseable", "detail": "..."}}`。

## 本地验证方法

```bash
# 安装依赖（uv）
uv sync

# 运行全部单测（日志默认打印每组用例的输入数据与判定依据，-s 可查看实时输出）
uv run pytest -s

# 启动服务
uv run python main.py
```

测试覆盖：

- **多发布线**：各线独立版本基线、无关标签被忽略并给出说明、共享已发布部分的
  跨线统一顺序、传线/传分支/导提交顺序无关性；
- **两种集成方式**：合并式保留合并点且父先于子、变基式拉直并丢弃合并提交
  （skipped 与 rationale 说明）、两种顺序在输入打乱后稳定一致、八爪鱼合并以
  `unrebaseable` 可区分地失败、已发布合并提交不参与 skipped；
- **批量导入与修订号**：失败批次状态与修订号均不变（冲突/缺失父提交/未知分支头
  三种失败）、修订号单调且重复导入不空涨、按修订号取增量不重不漏且排除已发布、
  越界修订号拒绝、并发导入下修订号与内容一一对应、回溯后修订号一致；
- **既有能力回归**：分叉合并拓扑序、循环与缺失父提交拒绝、预发布排序与构建
  元数据、重复导入幂等、分支输入顺序无关性、并发写入无丢失无重复、历史快照
  回溯可复现、旧格式缺省字段兼容。
