# 本地分支合并编排与多发布线版本规划

以本地导入的提交、分支与标签数据为输入，计算：

- 多条发布线**各自独立**的下一语义化版本号与变更日志；
- 同一批分支的**合并式**与**变基式**两套可执行顺序；
- **整批原子导入**、单调递增的**导入修订号**与未发布提交增量查询；
- 所有结论在不同操作顺序下保持一致，并输出可解释的判定依据（`rationale`）。

## 模块结构

| 模块 | 职责 |
| --- | --- |
| `release_planner/models.py` | `Commit` / `Tag` / `SemVer` / `MergePlan` / `LinePlan` / `MultiReleasePlan` / `RebasePlan` 等数据模型 |
| `release_planner/graph.py` | 提交图导入、校验（缺失父提交、循环父边、重复提交）与拓扑查询 |
| `release_planner/planner.py` | 单发布线的合并顺序、下一版本号、变更日志（原有能力，保持不变） |
| `release_planner/integration.py` | **多发布线编排**：每线独立版本基线、合并式/变基式顺序、不可变基结构判定 |
| `release_planner/store.py` | 线程安全存储、**整批原子导入**、**导入修订号与增量查询**、历史快照回溯、旧格式兼容 |
| `main.py` | FastAPI HTTP 接口 |

## 多发布线版本基线规则

给一批目标分支（每条分支是一条发布线），各线**独立**计算版本与变更日志：

1. **属于该线的标签**：标签指向的提交必须是该线分支头沿父边可达的祖先。
   只有这类标签参与该线的 semver 排序，取最高者为该线基线（无标签时为 `0.0.0`）。
2. **不属于该线的标签**：标签提交不在该线祖先历史中的，**完全不影响该线版本号**，
   但会在结果 `ignored_tags` 中逐个列出标签名、指向提交与忽略原因
   （“不属于该发布线，不参与该线版本基线”）。例如 release-2.x 线上的 `v2.5.0`
   不会抬高只从 1.x 基点延伸的 main 线版本。
3. **该线的待发布提交**：该线头可达、且不属于“该线任一祖先标签的祖先集合”的提交。
   版本提升仍取待发布提交的最高变更级别；预发布基线遇待发布变更毕业为正式版
   （规则与单发布线一致）。
4. 各线结论见 `MultiReleasePlan.lines`（`LinePlan`：基线标签、下一版本、
   changelog、使用/忽略的标签、待发布提交）。

### 跨线总执行顺序

- 合并式总顺序：各线待发布提交取**并集**后做确定性拓扑序（父先于子，同层按提交
  id 字典序）。多条线共用的已发布/未发布段在总顺序中**只出现一次**
  （`shared_commits` 明确列出）。
- 总顺序只取决于提交图与标签，不随分支传入顺序、提交导入顺序变化。

## 两种集成方式的顺序判定与失败条件

同一批分支分别由 `plan_merge()` 与 `plan_rebase()` 给出可执行顺序，
`plan_all()` 一次返回两套；两者都稳定、可复现。

### 合并式（`merge`，保留合并点）

- 待发布子图拓扑序：**父提交必先于子提交，合并提交在其全部父提交之后**，
  合并点完整保留；同层按提交 id 字典序出队。

### 变基式（`rebase`，拉成直线）

- 对每条发布线，把待发布区间内的提交按同样的确定性拓扑序排列：
  - 非合并提交（0/1 个父）**keep**，按线性顺序重放；
  - 合并提交（≥2 个父）**skip**：合并点不再保留，其各父分支上的变更已经由
    非合并提交在线性序列中重放。每个跳过的提交都在结果中给出 `skip` 步骤与原因，
    保留/跳过清单见 `RebasePlan.lines` 与 `RebasePlan.skipped`。
- 总的线性顺序为各线 keep 提交并集的确定性拓扑序，共用提交只出现一次。

**失败条件（与普通输入错误区分）**：以下结构无法安全拉成直线，`plan_rebase()`
抛出 `rebase_unsupported`（而非悄悄返回跑不通的顺序），可与
`missing_parent`/`cyclic_parent_edge` 等普通输入错误通过 `FailureReason` 区分：

| 结构 | 原因 |
| --- | --- |
| 邪恶合并（合并提交 `change != none`，自身携带语义变更） | 跳过合并点会丢失其变更 |
| 合并两条**无公共祖先**的历史 | 变基无法表达该合并点 |
| 章鱼合并（>2 个父提交） | 无法安全压平为一条直线 |

注意：普通的分叉合并（如 feature 合入 main，合并提交自身无额外变更）可以安全变基，
此时只有合并提交被 skip，功能提交全部保留。

## 整批导入与导入修订号语义

`RepoStore.import_batch(commits=..., tags=..., branches=...)` 把一批数据
（可同时含提交、标签、分支头）当成一个整体：

- **原子性（all-or-nothing）**：批次在锁内“先预校验、后落盘”——批内/与存量的
  提交内容冲突、标签同名冲突、标签或分支引用缺失等都会在任何修改前检出。
  失败后提交图、标签、分支、快照以及对外可见的**导入修订号都保持不变**，
  批次中其余合法部分也不会部分生效。
- **导入修订号**：从 `0` 开始，仅当批次真正引入了至少一个新提交时 `+1`。
  - 同一批数据重复导入没有新提交，修订号**不增长**，同一提交不会重复计入。
  - 修订号严格单调递增；并发批次在同一把互斥锁内依次提交，各自拿到互不相同的
    修订号，提交内容与“引入修订号”一一对应，不错位、不丢数据。
- **增量查询** `commits_since(rev)`：返回修订号 `rev` 之后引入、且截至当前
  **仍未发布**（不属于任何现存标签提交祖先）的提交，按 `(引入修订号, 提交 id)`
  稳定排序，跨批次去重，**不重不漏**；一旦被新标签发布，相应提交从增量中消失。
  查询越界修订号抛 `revision_not_found`。
- `import_commits()` / `import_records()` / `add_tag()` / `set_branch()` 均保留，
  内部走同一原子批次；`import_commits` 仍返回新增提交数。
- 快照同时保存当前修订号与“提交 → 引入修订号”账本，`checkout()` 回溯后
  修订号、内容与规划结论一致、可复现。

## 与旧数据/旧接口的兼容范围

- **旧格式记录**：`import_records()` 对缺失字段继续使用稳定缺省值
  （`parents=()`、`message=""`、`branch=""`、`change="patch"`）。
- **单发布线规划**：`ReleasePlanner.plan()` 与 `GET /plan` 原样保留，
  多发布线能力是新增的独立入口（`MultiLinePlanner`、`/release-lines/*`），
  原有分叉合并、预发布排序、重复导入幂等、历史回溯用例均不回归。
- **快照格式扩展**：快照元组新增了修订号与引入账本（仅内部结构），
  对外的 `snapshot()`/`checkout()`/`history_size()` 行为不变；
  旧的内存快照无需迁移（进程内数据结构，重新导入即可）。
- 失败原因仅**新增** `rebase_unsupported`、`revision_not_found`、
  `duplicate_tag`，不改动已有 reason 的取值。

## 失败原因一览

| reason | 触发条件 |
| --- | --- |
| `duplicate_commit` | 同一 id 以不同内容重复定义（含批内冲突） |
| `duplicate_tag` | 同名标签指向不同提交 |
| `missing_parent` | 父提交缺失 |
| `cyclic_parent_edge` | 父边成环 |
| `unknown_branch` | 分支头提交不存在 |
| `unknown_tag` | 标签指向的提交不存在 |
| `invalid_version` | 版本号无法解析 / 历史版本号越界 |
| `empty_plan` | 未提供任何分支 |
| `rebase_unsupported` | 结构不适合变基（邪恶合并 / 无公共祖先 / 章鱼合并） |
| `revision_not_found` | 查询的导入修订号超出 `[0, 当前]` 范围 |

## HTTP 接口

```text
POST /import                    整批原子导入 commits+tags+branches（返回新增数与修订号）
POST /commits                   仅批量导入提交（兼容旧接口，返回 added/revision）
POST /tags                      添加版本标签
POST /branches                  设置分支头
GET  /plan                      单发布线：合并顺序、下一版本、变更日志、判定依据
GET  /release-lines/plan        多发布线：各线版本/基线/忽略标签 + 合并式与变基式顺序
GET  /release-lines/rebase      多发布线：仅变基式顺序（不适用 -> 422 rebase_unsupported）
GET  /revision                  当前导入修订号
GET  /commits-since/{rev}       该修订号之后新增且未发布的提交（不重不漏）
POST /snapshots                 显式生成快照，返回版本号
POST /checkout/{ver}            回溯历史版本（修订号一并回溯）
```

错误响应形如：`409/404/422 {"detail": {"reason": "rebase_unsupported", "detail": "..."}}`。

## 本地验证方法

```bash
# 安装依赖（uv）
uv sync

# 运行全部单测（日志默认打印每组用例的输入数据与判定规则，-s 实时输出）
uv run pytest -s

# 只看新增能力
uv run pytest -s tests/test_multiline.py tests/test_integration_modes.py tests/test_revisions.py

# 启动服务
uv run python main.py
```

测试覆盖：

- 原有不回归：分叉合并拓扑序、循环/缺失父提交拒绝、预发布排序与构建元数据、
  重复导入幂等、分支输入顺序无关、并发写入无丢失无重复、快照回溯可复现、旧格式兼容；
- 多发布线：各线只按自己历史标签算版本、无关标签被忽略且说明原因、各线 changelog、
  跨线总顺序稳定、共用段去重；
- 两种集成：合并式保留合并点、变基式 skip 合并提交并拉直线、两套顺序与输入顺序
  无关、邪恶合并/无公共祖先/章鱼合并以 `rebase_unsupported` 显式失败且与普通
  输入错误可区分；
- 导入语义：整批失败后状态与修订号不变、重复批次修订号不涨、修订号单调递增、
  `commits_since` 不重不漏且发布后消失、并发导入修订号与内容一致。
